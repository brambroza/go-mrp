# วิเคราะห์โจทย์ใหม่ 6 ข้อ และแนวทางปรับระบบ

เขียน 2026-09-30 · สถานะ: **ข้อเสนอ รอเจ้าของตัดสินใจ** · ยังไม่ได้แก้โค้ดตามนี้

โจทย์จากลูกค้า (ตามที่เจ้าของส่งมา):

1. หน้างานไม่ยอมใช้ → ต้องคีย์ผ่านมือถือหรือ LINE ด้วยการสแกน QR แบบไม่ต้องอบรม
2. ขึ้นระบบนาน → ต้องนำเข้าข้อมูลจาก Excel ได้ และเห็นผลตั้งแต่วันแรก
3. ไม่รองรับโรงงานรับจ้างผลิต → ต้องใช้ job เป็นแกน รองรับงานที่ส่งไปจ้างข้างนอก และตามได้ว่าออเดอร์อยู่ขั้นไหน
4. ต้นทุนไม่แม่น → ต้องบอกกำไรจริงของแต่ละออเดอร์ได้
5. ทุกเจ้าบังคับเปลี่ยนระบบบัญชี → ต้องทำงานคู่กับ Express, PEAK หรือ FlowAccount ได้
6. มีข้อมูลแต่ไม่มีคำตอบ → ต้องให้เจ้าของถามข้อมูลผ่าน LINE ด้วย AI ได้

## 1. สรุปภาพรวม

โจทย์ทั้ง 6 ข้อ**ไม่ขัด**กับสิ่งที่สร้างไว้ (tenant, RLS, ledger, MRP, approval engine) แต่เปลี่ยน**จุดขายและลำดับงาน**:

| เดิม (docs/plan.md) | ใหม่ |
|---|---|
| แกนคือ SO → MRP → ใบสั่งผลิต (แบบโรงงานผลิตสินค้าตัวเอง) | แกนคือ **Job** (งานรับจ้างผลิตต่อออเดเดอร์) ที่มี MRP / ใบสั่งผลิต / จ้างนอก / ต้นทุน ห้อยอยู่ใต้ job |
| หน้างานใช้แอป Expo ที่ต้อง login | หน้างานใช้ **LINE + QR** ไม่ต้อง login ไม่ต้องอบรม; Expo เก็บไว้สำหรับคลังที่ต้อง offline |
| คีย์ master เอง | **นำเข้า Excel** เป็นทางหลักของการขึ้นระบบ |
| บัญชี export "ให้โปรแกรมบัญชี" (ยังไม่ระบุ) | เชื่อม **Express / PEAK / FlowAccount** เป็นชื่อเฉพาะ |
| Dashboard บน web | **ถามผ่าน LINE ด้วย AI** |

สิ่งที่ใช้ต่อได้ทั้งหมด: Platform, Masters, Inventory ledger, Purchasing, BOM/MRP/Work order, approval engine, RLS
สิ่งที่ต้องเพิ่ม: โมดูล Jobs (+ จ้างนอก + ต้นทุน), Imports, LINE (Login / LIFF / Messaging), Accounting connectors, AI assistant
สิ่งที่ต้องเปลี่ยนการตัดสินใจเดิม: ช่องทางหน้างาน (ข้อ 2 ด้านล่าง) — เป็น architecture change ต้องให้ Technical Lead / เจ้าของอนุมัติ

## 2. วิเคราะห์ทีละข้อ

### ข้อ 1 — หน้างานไม่ยอมใช้: LINE + QR ไม่ต้องอบรม

**ปัญหาจริง:** พนักงานหน้างานไม่จำรหัสผ่าน ไม่ติดตั้งแอป ไม่อ่านเมนู งานหน้างานมีแค่ 4–5 อย่าง: รับงาน, เบิกของ, บอกว่าทำเสร็จเท่าไร, ของเสียเท่าไร, ส่งต่อขั้นถัดไป

**สิ่งที่มีแล้ว:** แอป Expo (login + สแกน + offline queue) — ครบแต่ต้องอบรมและต้องติดตั้ง

**แนวทาง:**
- ทุกเอกสารหน้างานมี **QR** พิมพ์ติด: ใบสั่งผลิต (ต่อขั้นตอน), lot / พาเลท, ตำแหน่งเก็บ, เครื่อง
- พนักงานสแกน QR ด้วยกล้อง LINE → เปิด **LIFF** (เว็บใน LINE) → เห็นหน้าเดียวที่ถามสิ่งเดียว เช่น "WO-0004 ขั้นบรรจุ — ทำได้กี่ชิ้น?" + ปุ่มใหญ่ 1–3 ปุ่ม → กดส่ง จบ
- ตัวตน = LINE user id ที่ผูกกับผู้ใช้ของบริษัทครั้งเดียว (หัวหน้าส่งลิงก์เชิญทาง LINE กลุ่ม กดยอมรับ = ผูกเสร็จ) ไม่มีรหัสผ่านสำหรับหน้างาน
- QR มี token สั้นที่ลงนามโดย server (ไม่ใช่ id ตรงๆ) หมดอายุได้ และผูกกับ tenant → สแกน QR ของบริษัทอื่นไม่ได้
- แจ้งเตือนกลับทาง LINE: "งานถัดไปของคุณ", "ของขาด", ปุ่มอนุมัติในข้อความ (Flex Message) สำหรับหัวหน้า
- Expo เก็บไว้เฉพาะงานคลังที่ต้อง offline / สแกนต่อเนื่องเร็วๆ (รับของหลายสิบบรรทัด, นับสต็อก)

**ต้องเพิ่มใน API:** `POST /auth/line` (ตรวจ id token ของ LINE Login), ตาราง `platform.user_channels(user_id, channel=LINE, external_id)`, `platform.qr_tokens` หรือ token แบบลงนาม, endpoint "quick action" ต่อชนิด QR (`POST /shopfloor/scan` → บอกว่า QR นี้คืออะไรและทำอะไรได้), LINE Messaging webhook + ส่งข้อความ
**Tenant setting:** LINE channel ของแต่ละบริษัท (ลูกค้าใช้ LINE OA ของตัวเอง) หรือใช้ OA กลางของเรา — ต้องตัดสินใจ (ดูข้อ 5)

**ความเสี่ยง:** LIFF ต้องออนไลน์ (หน้างานที่สัญญาณไม่ดีต้องใช้ Expo); LINE เปลี่ยนนโยบาย/ราคา OA ได้; ต้องมี LINE Developer account ต่อลูกค้าหรือของเรา

### ข้อ 2 — ขึ้นระบบนาน: นำเข้า Excel และเห็นผลวันแรก

**สิ่งที่มีแล้ว:** API สร้าง master ทีละรายการ; ไม่มี import

**แนวทาง — Import wizard 3 ขั้น (อัปโหลด → ตรวจและแสดงตัวอย่าง → ยืนยัน):**

| ลำดับ | นำเข้า | หมายเหตุ |
|---|---|---|
| 1 | หน่วยนับ, กลุ่ม, สินค้า/วัตถุดิบ | สร้างหน่วยที่ยังไม่มีให้อัตโนมัติ |
| 2 | ลูกค้า, ผู้ขาย | |
| 3 | BOM / สูตร | 1 แถวต่อ component; สร้างเป็น version 1 สถานะ Active |
| 4 | **ยอดสต็อกยกมา** ต่อ lot (หรือต่อสินค้าถ้าไม่มี lot) | บันทึกเป็นใบปรับสต็อก เหตุผล `OPENING` → เข้า ledger ตามปกติ ต้นทุนตามที่กรอก |
| 5 | PO ค้างรับ, job/ออเดอร์ค้าง | เพื่อให้วันแรกเห็นงานจริง |

- Template Excel ภาษาไทยดาวน์โหลดได้ พร้อมตัวอย่าง 3 แถว; รับทั้ง `.xlsx` และ `.csv`
- ตรวจทุกแถวก่อน commit: รหัสซ้ำ, หน่วยไม่รู้จัก, BOM อ้างสินค้าที่ไม่มี → แสดงตารางผลตรวจ แก้ใน Excel แล้วอัปโหลดใหม่ หรือ "ข้ามแถวที่ผิด"
- Import ซ้ำได้: แถวที่รหัสตรงกัน = อัปเดต (upsert) — ทำให้ลูกค้าโยนไฟล์เดิมซ้ำได้โดยไม่พัง
- ทำใน transaction เดียวต่อไฟล์; มี job ประวัติการนำเข้า (ใครนำเข้าอะไรเมื่อไร กี่แถว)
- "เห็นผลวันแรก" = หลัง import ข้อ 1–4 หน้าแรกแสดงทันที: สต็อกคงเหลือ, ของต่ำกว่า safety, งานค้าง; รัน MRP ได้เลย

**ต้องเพิ่มใน API:** โมดูล `Imports` (`POST /imports/{type}/validate`, `POST /imports/{type}/commit`, `GET /imports/templates/{type}`), อ่าน xlsx (ClosedXML หรือ ExcelDataReader), เหตุผลปรับ `OPENING`, ทำเป็น Hangfire job สำหรับไฟล์ใหญ่
**ทำได้เร็ว:** ใช้ service ที่มีอยู่ (MasterCrud, BomService, StockDocumentService) ไม่ต้องเขียน logic ใหม่

### ข้อ 3 — โรงงานรับจ้างผลิต: Job เป็นแกน + จ้างนอก + ตามสถานะ

**ช่องว่างใหญ่ที่สุด** ระบบตอนนี้คิดแบบโรงงานผลิตสินค้าของตัวเอง (demand → MRP → WO) ไม่มี "ออเดอร์ของลูกค้า" เป็นวัตถุหลัก

**แนวทาง — โมดูล `Jobs`:**

```
Job (ออเดอร์รับจ้าง 1 ใบ)
 ├ ลูกค้า, สินค้า/สเปคที่รับจ้าง, จำนวน, กำหนดส่ง, ราคาตกลง (ต่อหน่วย / เหมา), เลข PO ของลูกค้า
 ├ BOM ของ job (คัดลอกจากสูตรมาตรฐาน แล้วแก้เฉพาะ job ได้ — OEM เครื่องสำอางแต่ละลูกค้าสูตรต่างกัน)
 ├ ขั้นตอน (routing ของ job): แต่ละขั้นเป็น "ทำเอง" หรือ "จ้างนอก"
 ├ ใบสั่งผลิต (WO) ต่อขั้นทำเอง  ← ใช้ production.work_orders ที่มี เพิ่ม job_id
 ├ ใบจ้างนอก (Subcontract order) ต่อขั้นจ้างนอก  ← PO ประเภทบริการ + เบิกวัตถุดิบไป "คลังผู้รับจ้าง" + รับงานกลับ
 ├ PR/PO วัตถุดิบที่ซื้อเพื่อ job นี้  ← MRP ที่รันเฉพาะ job (pegging ถึง job)
 ├ ส่งมอบ (delivery) และ invoice  ← เฟส 4
 └ ต้นทุน + กำไร (ข้อ 4)
```

- **สถานะ job derive จากเอกสารลูก** ไม่ให้คนคีย์: รับงาน → รอวัตถุดิบ (PO ยังไม่ครบ) → กำลังผลิต (WO ขั้นไหน) → อยู่ที่ผู้รับจ้าง (ใบจ้างนอกยังไม่รับกลับ) → รอ QC → พร้อมส่ง → ส่งแล้ว → ปิด
  แสดงเป็น timeline ต่อ job และตารางรวม "ออเดอร์ทั้งหมดอยู่ขั้นไหน" (เหมือน tracking พัสดุ) — นี่คือหน้าที่เจ้าของเปิดทุกเช้า
- **จ้างนอก:** ผู้รับจ้างเป็น supplier + มี warehouse ประเภทใหม่ `Subcontractor` ผูกกับ supplier; ส่งวัตถุดิบ = ใบโอนไปคลังนั้น (ยังเป็นสต็อกของเรา ต้นทุนติดตาม job); รับงานกลับ = ใบรับที่อ้างใบจ้างนอก สร้าง lot ของสินค้าขั้นถัดไป ค่าจ้างเข้าต้นทุน job; ของเสียที่ผู้รับจ้างทำ = ปรับสต็อกที่คลังผู้รับจ้าง เหตุผล `SUBCON_LOSS`
- **QR ต่อขั้น** (ข้อ 1) ทำให้หน้างานอัปเดตขั้นของ job ได้โดยไม่รู้ว่าระบบชื่ออะไร
- MRP: เพิ่ม demand จาก job (แทน demand กรอกเอง) และ pegging ต้นเหตุ = เลข job — engine ที่มีรองรับอยู่แล้ว (`Pegging`)

**ต้องเพิ่มใน API:** schema `jobs` (jobs, job_steps, job_boms, subcontract_orders/_lines), warehouse type `Subcontractor`, `job_id` บน work_orders / purchase_request_lines / demands / stock_documents, `GET /jobs/{id}/timeline`, `GET /jobs/board`
**กระทบสเปคเดิม:** `docs/specs/production-planning.md` §demand → demand มาจาก job; `inventory.md` เพิ่ม warehouse type

### ข้อ 4 — ต้นทุนไม่แม่น: กำไรจริงต่อออเดอร์

**สิ่งที่มีแล้ว:** ledger เก็บต้นทุนต่อหน่วยของทุก movement (FIFO ต่อ lot), PO มียอดเงิน, WO รู้ว่าเบิกอะไรไปเท่าไร — **ครึ่งหนึ่งของ job costing มีข้อมูลอยู่แล้ว**
**ที่ขาด:** ค่าแรง/ชั่วโมงเครื่อง (ยังไม่มีบันทึกผลผลิต), ค่าจ้างนอก (ข้อ 3), รายได้ต่อ job, overhead

**สูตรที่เสนอ (ต่อ job):**

```
ต้นทุนวัตถุดิบ   = Σ (ปริมาณที่เบิกให้ WO ของ job × ต้นทุน lot ตอนเบิก)  − ของที่คืนคลัง
ต้นทุนจ้างนอก   = Σ ยอดใบจ้างนอกที่รับงานกลับแล้ว (ตามจำนวนที่รับจริง)
ต้นทุนแรงงาน    = Σ (ชั่วโมงคน × อัตราต่อชั่วโมงของ tenant/แผนก)   ← จากบันทึกผลผลิตต่อ WO
ต้นทุนเครื่อง    = Σ (ชั่วโมงเครื่อง × อัตราต่อชั่วโมงของเครื่อง)          ← optional
Overhead        = (วัตถุดิบ + แรงงาน) × % ของ tenant  หรือ  บาทต่อชั่วโมง  ← tenant setting
ต้นทุนรวม       = ผลรวมข้างบน ;  ต้นทุน/หน่วย = ต้นทุนรวม ÷ จำนวนดีที่ส่งมอบ
รายได้           = ราคาตกลง × จำนวนส่งมอบ (หรือยอด invoice เมื่อมีเฟส 4)
กำไร            = รายได้ − ต้นทุนรวม ; margin % = กำไร ÷ รายได้
```

- แยก **ประมาณการ** (ตอนรับงาน: BOM × ราคาซื้อล่าสุด + เวลาตามมาตรฐาน) กับ **จริง** (จากเอกสาร) → หน้า job แสดงเทียบกัน เจ้าของเห็นทันทีว่า job ไหนกำไรหายเพราะอะไร (ของเสียเกิน, ซื้อแพงกว่าที่คิด, จ้างนอกแพง)
- ของเสีย/ loss ที่บันทึกตอนผลผลิตเข้าเป็นต้นทุนของ job (ไม่ใช่กรอกมือแบบระบบเดิม)
- ต้นทุนถูกผูกกับ ledger ที่แก้ไม่ได้ → ตัวเลขตรวจย้อนได้ทุกบาท

**ต้องเพิ่มใน API:** บันทึกผลผลิตต่อ WO (จำนวนดี, เสีย, ชั่วโมงคน, ชั่วโมงเครื่อง — หน้าเดียว กรอกผ่าน QR), ตาราง `jobs.job_cost_snapshots` (คำนวณเมื่อเอกสารเปลี่ยน หรือ on-demand ด้วย Dapper), tenant settings อัตราค่าแรง/overhead, `GET /jobs/{id}/profit`, รายงานกำไรต่อ job / ต่อลูกค้า / ต่อเดือน
**Golden test:** job ตัวอย่าง 1 ใบ คำนวณมือ (วัตถุดิบ 2 lot ต้นทุนต่างกัน + จ้างนอก + แรงงาน + overhead)

### ข้อ 5 — ทำงานคู่กับ Express / PEAK / FlowAccount

**ยืนยันกับหลักเดิม:** ไม่ทำบัญชีเอง ถูกต้องแล้ว แต่ต้องเชื่อมให้ "ไม่ต้องคีย์ซ้ำ" ไม่ใช่แค่ export

**สิ่งที่ต้องส่งไปบัญชี (จากระบบเรา):**

| เอกสารเรา | ไปเป็นอะไรในบัญชี | เมื่อไร |
|---|---|---|
| ใบรับของตาม PO | ใบรับสินค้า / บิลซื้อ (AP) | เมื่อ GR posted |
| ใบคืนผู้ขาย | ใบลดหนี้ซื้อ | เมื่อ RTS posted |
| ใบจ้างนอกที่รับงานกลับ | บิลค่าใช้จ่าย / AP | เมื่อรับกลับ |
| ส่งมอบ job / invoice | ใบส่งของ / ใบกำกับภาษี (AR) | เมื่อส่งมอบ (เฟส 4) |
| ปิดงวดสต็อก | ยอดสต็อกคงเหลือ (มูลค่า) | สิ้นเดือน |
| master ลูกค้า / ผู้ขาย / สินค้า | คู่ค้า / สินค้า | เมื่อสร้างหรือแก้ |

**แนวทาง — ชั้น "Accounting connector" 1 interface หลาย adapter:**
- ระบบเราออก "รายการบัญชีมาตรฐาน" กลาง (partner, item, doc, line, VAT) แล้ว adapter แปลงต่อปลายทาง
- **FlowAccount** และ **PEAK**: มี API (ต้อง**ตรวจเอกสาร API ปัจจุบัน**ก่อน — ผมยังไม่ได้ตรวจใน session นี้ ทั้งขอบเขต endpoint, การขอ token, และเงื่อนไขการใช้) → ส่งอัตโนมัติเป็น job พร้อม retry + log + สถานะต่อเอกสาร (ส่งแล้ว / รอ / ผิดพลาด) ให้ผู้ใช้เห็น
- **Express**: เป็นโปรแกรม desktop ไม่มี API สาธารณะ → export ไฟล์ตามรูปแบบ import ของ Express (ต้อง**ขอตัวอย่างไฟล์จากลูกค้าที่ใช้ Express**) กดดาวน์โหลดรายวัน/รายเดือน
- **ผังบัญชี (mapping)** ตั้งต่อ tenant: กลุ่มสินค้า → รหัสบัญชี, VAT, คู่ค้า → รหัสในโปรแกรมบัญชี; mapping ที่ยังไม่ครบ = เอกสารค้างส่ง ไม่ส่งผิด
- ทางเดียว (เรา → บัญชี) ก่อน; ดึงยอดรับชำระกลับมาเพื่อ credit check ทำทีหลัง

**ต้องเพิ่มใน API:** โมดูล `Accounting` (mappings, outbox ต่อเอกสาร, adapters), Hangfire สำหรับส่ง, หน้า "รายการรอส่งบัญชี"
**ความเสี่ยงสูง:** API ของ PEAK / FlowAccount อาจจำกัดแพ็ก, rate limit, หรือไม่รองรับบางเอกสาร — ต้องทดสอบด้วยบัญชีทดลองก่อนสัญญากับลูกค้า

### ข้อ 6 — ถามข้อมูลผ่าน LINE ด้วย AI

**แนวทาง:** เจ้าของพิมพ์ใน LINE OA ว่า "งาน ABC อยู่ขั้นไหน", "เดือนนี้กำไร job ไหนต่ำสุด", "น้ำมันมะพร้าวพอผลิตถึงเมื่อไร" → bot ตอบจากข้อมูลของบริษัทนั้น
- **ไม่ให้ AI เขียน SQL เอง** ให้ AI เลือกใช้ "เครื่องมือ" ที่กำหนดไว้ (tool use) เช่น `job_status(job_no)`, `stock_on_hand(item)`, `job_profit(period)`, `open_purchase_orders()`, `mrp_shortages()` — แต่ละเครื่องมือเรียก service เดิมที่ผ่าน RLS ด้วย role อ่านอย่างเดียว → ข้อมูลรั่วข้ามบริษัทไม่ได้ และ AI ทำอะไรที่เปลี่ยนข้อมูลไม่ได้
- ตัวตน: LINE user ที่ผูกกับผู้ใช้ที่มีสิทธิ์ (ข้อ 1) → สิทธิ์เดียวกับ web; คนที่ไม่ได้ผูก bot ไม่ตอบ
- คำตอบมาพร้อมตัวเลขและลิงก์เปิด web/LIFF ดูรายละเอียด; ถ้าเครื่องมือไม่มีคำตอบ bot บอกว่าไม่รู้ ไม่เดา
- เก็บ log คำถาม-คำตอบ-เครื่องมือที่เรียก ต่อ tenant (ตรวจย้อนได้ + ใช้ปรับปรุง)
- โมเดล: Claude รุ่นล่าสุด ผ่าน Anthropic API; ตั้งเพดานค่าใช้จ่ายต่อ tenant ต่อเดือน; ภาษาไทย
- ทำหลังข้อ 3–4 เพราะคำถามที่มีค่าที่สุดคือเรื่อง job และกำไร ซึ่งต้องมีข้อมูลก่อน

**ต้องเพิ่มใน API:** `Assistant` module (webhook LINE → ตรวจผู้ใช้ → เรียก Claude พร้อม tool definitions → ตอบกลับ), ชุดเครื่องมืออ่านอย่างเดียว, log
**ต้นทุนต่อคำถาม:** ประมาณหลักสตางค์ถึงไม่กี่บาท ขึ้นกับความยาว — รวมในแพ็ก Pro ขึ้นไปพร้อมโควตา

## 3. ผลต่อแพ็กเกจและราคา (ข้อเสนอ)

| แพ็ก | เดิม | ใหม่ (เสนอ) |
|---|---|---|
| Starter | คลัง + จัดซื้อ | + นำเข้า Excel, LINE QR หน้างาน (รับของ/เบิก), export บัญชี (Express ไฟล์) |
| Pro | + BOM/MRP/ผลิต | + **Job + ต้นทุน/กำไรต่อ job + จ้างนอก**, เชื่อม PEAK/FlowAccount อัตโนมัติ, AI ถามผ่าน LINE (โควตา) |
| Enterprise | + ขาย/invoice, Lab, API | เหมือนเดิม + AI ไม่จำกัด, connector เพิ่มตามลูกค้า |

จุดขายหลักเปลี่ยนจาก "MRP" เป็น **"รู้ว่าทุกออเดอร์อยู่ไหนและกำไรเท่าไร โดยหน้างานไม่ต้องอบรม"** — MRP กลายเป็นของแถมที่คู่แข่ง SME ไม่มี

## 5. ต้องตัดสินใจก่อนเริ่ม (ถามเจ้าของ)

1. **LINE OA ของใคร:** ลูกค้าแต่ละรายใช้ OA ของตัวเอง (ต้องตั้งค่าต่อราย ค่า OA เป็นของลูกค้า) หรือใช้ OA กลางของเรา (ตั้งค่าครั้งเดียว แต่ข้อความทั้งหมดผ่านชื่อเรา และค่าข้อความเป็นของเรา) — ผมแนะนำ **OA ของลูกค้า** สำหรับ Pro/Enterprise และ OA กลางสำหรับ Starter
2. **Expo ยังทำต่อไหม:** เก็บไว้เฉพาะคลัง (offline) ตามเสนอ หรือหยุดพัฒนาแล้วใช้ LIFF ทั้งหมด — กระทบงานที่ agent ทำไว้ใน `mobile/`
3. **ลำดับ connector บัญชี:** ลูกค้ากลุ่มแรกใช้โปรแกรมไหนมากที่สุด — เริ่มจากตัวนั้น; ต้องมีบัญชีทดลองของ PEAK และ FlowAccount และตัวอย่างไฟล์ import ของ Express
4. **นิยาม "job":** 1 job = 1 PO ของลูกค้า หรือ 1 job = 1 สินค้าใน PO (PO มีหลายสินค้า → หลาย job) — กระทบต้นทุนต่อ job และการเสนอราคา ผมแนะนำ **1 job = 1 สินค้า × 1 ออเดอร์** และมี "ออเดอร์" ครอบหลาย job
5. **AI:** ยอมรับต้นทุนต่อคำถามและการส่งข้อมูลธุรกิจของลูกค้าไปยังผู้ให้บริการโมเดลไหม (ต้องระบุใน DPA/สัญญาลูกค้า)
6. **ลูกค้าอ้างอิงจริง 1 ราย** สำหรับข้อ 3–4: ต้องมีโรงงานรับจ้างที่ยอมให้ดู flow จ้างนอกและวิธีคิดต้นทุนจริง ไม่งั้นออกแบบจากการเดา

## 6. สิ่งที่ยังไม่ได้ทำใน session นี้

- ยังไม่ได้แก้โค้ด, spec, หรือ CLAUDE.md ตามข้อเสนอนี้ — รอการตัดสินใจข้อ 5
- ยังไม่ได้ตรวจเอกสาร API ของ PEAK / FlowAccount / LINE (ค้นเว็บไม่ได้ใน session นี้) — ตัวเลขและความสามารถที่อ้างถึงต้องตรวจซ้ำ
- ประมาณการเวลายังไม่ให้ เพราะขึ้นกับข้อ 5 และผลตรวจ API
